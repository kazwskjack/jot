# Delivery flow v1 metrics

`metrics.py` reads owner JSONL streams and emits a derived JSON snapshot. It never writes the formal AC ledger.

```powershell
python tools/delivery-flow-v1/metrics.py --events docs/delivery-flow-v1/events/owner-13.jsonl docs/delivery-flow-v1/events/owner-20.jsonl --evidence-root . --output docs/delivery-flow-v1/metrics-snapshot.json
```

Each event is one append-only transition. Workflow events include `ready`, `received`, `integrated`, `test`, `rework`, and `accepted`; R3 timing events add `product_work_started`, `blocked`, `resumed`, and `next_primary`. Events use UTC `occurred_at`, a stable `event_id`, producer `owner`, and immutable `source_class` (`inherited_wip` or `new_development`). In R3, `task_owner` is the responsible worker slot and `task_id` is its original primary or backup AC ID; they are checked against the fixed start pin's work orders. `owner` remains the event producer and may differ from `task_owner`. Queue-stage `packet_id` remains the unique source package/revision identity and is never inferred from `task_id`. Identical event IDs are counted once; a conflicting payload for an existing ID fails the rollup. Files may arrive out of order; stage durations use event time. Unknown fields are accepted and ignored in derived metrics; source event files are never rewritten.

R3 events carry `trial_id` and a strict `timestamp_provenance` object with `basis` plus nullable `process_observed_at`, `actor_reported_at`, and `native_observed_at`. The selected basis timestamp must equal `occurred_at`. `actor_reported` is a participant's report, `process_observed` is emitted from a real process/queue observation, and `native_observed` comes from a native product timestamp. These sources stay separate in interval summaries. Active flags and event counts are workflow state; they are not concurrency or productivity measurements. An interval with a missing or ambiguous endpoint is reported as unknown, never as zero.

The `work_event.py` recorder only appends the current worker's own actor-reported events; it does not run product commands, choose a time basis, or accept a caller-supplied output path or source class. It resolves the worker from the exact current private workspace in the R3-pinned assignments, resolves `source_class` from the matching pinned work order, and writes under that workspace's `private/reports/r3/owner-N.jsonl`. The fixed profile, immutable start pin, snapshot, 120-minute start window, work-order hashes and task mapping must all validate before `start` can be recorded. A prepared snapshot is not a start authorization. Its `packet_id` is `actor-task:<task_owner>:<task_id>`, a reserved task grouping key, not a source packet ID. R3 actor-reported events are excluded from queue snapshot reconstruction and source-packet summaries; their source-labeled work, blocked-wait and ready-to-next-primary intervals appear in `task_timing_summaries`, split by producer `owner`. The actual process observer must emit its own queue event with the true source package/revision ID and frozen candidate commit/tree. Source packet IDs may not use the reserved `actor-task:` prefix. Process-observed events are emitted by their actual producer, not by this self-report recorder.

`test` events need a job ID, integer exit code, string result (`passed` or `failed`), and local result file with matching SHA-256; `passed` requires exit code 0. `accepted` records workflow progress only and is not a formal AC acceptance or status change. This tool reports no formal D/E counts and cannot promote ACs; formal comparison remains with owner 14 against the existing canonical ledger, with R reporting the result. Evidence paths must resolve inside `--evidence-root`.

`trial.schema.json` describes a product-only 120-minute record. `metrics.py` validates the full schema, including strict nested fields, candidate commit/tree, packet sets, and event-stream references. For every non-null snapshot it verifies each stream stays under `--evidence-root`, matches its SHA-256, parses as a valid owner stream, has no event after `captured_at`, and reconstructs exact queue packet sets from each source packet's last non-actor event: `ready` is ready; `received`, `integrated`, `test`, and `rework` are active; `accepted` is terminal. R3 actor-reported events cannot create or replace queue packet state. Same-packet events with equal timestamps are rejected as ambiguous; event IDs are never used to invent an ordering. Every listed current packet's last event must match the snapshot candidate. The optimization baseline candidate must match the start snapshot; snapshot timestamps must match their trial boundaries.

The legacy R2 records continue to use only their fixed R2 snapshot pin. R3 records and R3 metrics rollups use the fixed runtime profile `docs/diagnostics/delivery-flow-v3-20261025/runtime-profile.json` and its independently pinned SHA-256, not a path or hash supplied by the record or CLI. The profile pins `workers.json` and `dispatch-policy.json`; the immutable `trial-start-pin.json` pins exact snapshot bytes and must name the same R3 trial ID. The snapshot carries that ID at the top level; its nested `trial` object must attest `started: true`, `real_product_trial_started: true`, and UTC `started_at`/`ends_at` exactly 7,200 seconds apart. It also pins each worker work-order path and byte hash, primary/backup IDs, and source-class map. Each work-order path is derived from the fixed assignments path and worker number, then cross-checked against those snapshot fields. Every R3 event is checked against this map: `task_owner` and `task_id` must match a pinned work order and `source_class` must match its map; `owner` remains the producer. Queue events retain source packet IDs, while actor reports use the reserved task grouping key described above. No caller-selected authorization path or hash is accepted. Until R issues a real immutable start pin, all R3 metrics rollups, running/completed records and recorder `start` events reject; the prepared template remains valid without start evidence. No authorization field or second ledger was added to `trial.schema.json`.

The record contains no formal D/E count. `trial-preparation.json` preserves the historical 3.951902-hour / 8-batch baseline; it includes inherited WIP without a source-class split, and has null start/end snapshots. Its `prepared_not_started` state is deliberate. Tooling, synthetic integration, environment preparation and inherited WIP are excluded from the product trial. Populate product inputs and start snapshot only after R freezes the real-Jot candidate and issues `trial_start`. Do not treat the historical baseline as a current prediction.
