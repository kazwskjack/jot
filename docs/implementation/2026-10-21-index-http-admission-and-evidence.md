# Original Git index HTTP admission and evidence

This continuation keeps the original Jot/DSH planner, owned project, database,
review and execution journal. HTTP admission commits an original acceptance;
it does not dispatch Git, reserve a workspace, acquire a Worker or invoke a
native Host. Selected Apply, authenticated dispatch/recovery, mobile workflow
and the wider Git/all-capability acceptance remain separate unfinished work.

## Connected original boundaries

- `POST /v1/projects/{projectId}/git/intents/{intentId}/admissions` accepts only
  the original request ID, review version and review digest. Original execution
  and HTTP acknowledgement commit in the existing immediate transaction.
- `POST /v1/projects/{projectId}/git/executions/{executionId}/controls` commits
  the exact original explicit control: request ID, inspection digest and unknown
  acknowledgement. It grants no execution permission and performs no cleanup.
- Inspection, control-admission and control-receipt GET routes reuse original
  readers and require UI admission. They cannot adopt trusted internal work.
  Existing immutable acceptance and current-result routes remain distinct.
- The original server pre-cache boundary checks current owner and configured
  repository readiness. CSRF, exact request hash and the original idempotency
  key remain required. A cached acceptance cannot bypass transfer or readiness.
- Separate atomic protocol identifiers distinguish index acceptance and control
  acceptance. A legacy pending HTTP record cannot resume as either new protocol.
  Failure to commit the HTTP acknowledgement rolls the business acceptance back;
  restart can recover the same original pending request without duplicating it.

OpenAPI JSON/YAML, operation manifest, event-schema definitions and shared types
describe the same five operations and strict request/response structures. Extra
roots, commands, owners and mixed publication-control fields are rejected.
Completed control receipts cannot contain a pending execution result. Control
completion still does not imply native settlement; the original native drain
proof remains separately required before releasing a held workspace.

## Frontend connection

The existing workbench client uses the existing BFF route family and shared
authenticated JSON request helper. Admission methods take an explicit reusable
HTTP key; original command bodies remain unchanged across a retry. Evidence
reads are no-store and cancellable. No frontend method retries an unknown
physical effect, accepts a Host/root or supplies a user identity.

This is the typed request layer, not actual selected Apply UI or a claim of a
completed mobile/BFF/native flow. Actual BFF integration and user interaction
acceptance remain to execute before enabling that workflow.
